# Writing the changelog and roadmap

Rules for the copy in `src/data/changelog-notes.ts` and
`src/data/roadmap-entries.ts`, for people and for the daily changelog job alike.

Both: contractions, British spelling, no em dashes. "You" is the person using
Antgrid; say "we" only to own something, such as a bug we shipped or a call we
made. Never write "bug fixes and improvements", hype (seamless, effortless,
supercharge, unlock, blazing-fast) or vague comparisons with unnamed rivals.
Name the rival if you compare.

Older copy predates these rules. Leave old changelog notes alone, because they
are a record. Bring a roadmap entry in line when you next update it.

## Changelog

`src/data/changelog-releases.ts` is generated by `bun run sync:changelog`; never
edit it. Notes go in `changelog-notes.ts`, one key per release tag. A release
without a key still shows, linked to its GitHub notes, so add one only when a
user would notice something. Maintenance releases get no key.

- **One change per line, the most noticed first.** The page renders lines in
  the order written. A fix is one sentence of at most 25 words: what went wrong
  and what happens now. Anything else gets up to three sentences: what you can
  do, where to find it, and the limit that matters, such as "while the desktop
  app is open".
- **Say where.** Name the screen or agent as the app names it. No PR numbers,
  module names or code names.
- **Prefixes lead.** `Action needed:` comes first, then the platform or agent
  the line applies to: `Windows: …`, `Codex: …`.
- **Action needed.** If anyone has to update, reconnect or change a setting,
  start the line `Action needed:`, say who must do what and what breaks if they
  don't (with minimum app and bridge versions), and put it first in the
  release. It keeps its honest kind.
- **Pick the kind honestly.** `new`: you couldn't do it before. `changed`: it
  works differently, or it's gone. `fixed`: it was broken and isn't.
  `security`: it changes who can reach your machine, what runs on it without
  your say, or what leaves it, such as a prompt that ran as a shell command, a
  signed-out session that could still see your account or a link built to
  mislead. Say which versions were affected and link the advisory if there is
  one, with no more detail than it gives. Faster crypto isn't `security`.
- **Own regressions, flag known issues, give credit.** A fix for something a
  recent release broke names that release. A known issue goes last, as a
  `changed` line starting `Known issue:`. End a line with "Thanks to @handle"
  for an outside contributor, or a reporter who agrees to it.
- **Titles are optional.** Set one only when the release has a clear
  through-line.
- **Only what shipped.** Nothing that isn't in the released tag: development-only
  work and roadmap items haven't shipped.
- **Pulled releases.** Don't delete a bad release on GitHub. Make its first line
  `Action needed:` naming the version to install instead. If one is deleted
  anyway, its note is orphaned and the unit tests fail: move anything still true
  to the next release and remove the key.

One line doing three jobs:

```ts
["fixed", "We've caught up with recent Claude Code releases. Sessions aren't named after a slash command or a compaction summary, and an account hold or credential error comes straight to you instead of the agent being told to continue."],
```

Split, with the first sentence gone because it's about us, not you:

```ts
["fixed", "Claude Code: sessions are no longer named after a slash command or a compaction summary."],
["fixed", "Claude Code: an account hold or credential error now reaches you, instead of the agent being told to carry on."],
```

## Roadmap

Each entry is product copy: say what you'll be able to do, not how it's built.

- **Statuses.** `now`: being built, five at most. `next`: planned, not started.
  `exploring`: an idea, not a commitment. `done`: in a published app release,
  or live on antgrid.ai for `area: "Website"` entries.
- **Done means released.** A merged PR isn't done. Once a published release
  contains the feature, set `status: "done"`, `updatedAt` to the release date
  (not the day you edit) and `releaseUrl` to
  `https://antgrid.ai/changelog#<tag>`, such as `#v1.20750.1036`. The tag must
  already be in `changelog-releases.ts`. Website entries have no `releaseUrl`;
  every new app entry must have one.
- **`title`** names the capability as the app will: "Voice input", not the
  project behind it.
- **`description`** is the benefit in one sentence. It doesn't change as the
  work progresses.
- **`update`** starts with the stage (Exploring, Designing, Building, Testing,
  Early access), then says where it stands and which platforms it doesn't cover
  yet. No branches, PRs or "platform integration", and no dates. A `done`
  update starts `Completed:` and says in one or two sentences what shipped,
  limits included.
- **`discussionUrl`** is optional and goes where you can comment: a GitHub
  Discussion or issue, not a PR.
- **`updatedAt`** is when the entry last changed in substance.
- **`LAST_REVIEWED`** means someone has checked that every entry is still true,
  so no `updatedAt` may be later. If your change pushes one past it, your PR is
  the review: check every other entry, then move `LAST_REVIEWED` to today.
- **Stopping.** If work stalls, say so or move it back to `next`. If it's
  cancelled, keep it under `exploring` for a release with an update starting
  `Not pursuing:` and one reason, then remove it. Ids are page anchors, so never
  reuse one.
- **Never list** work nobody is doing, or anything unannounced: pricing changes,
  partners, unreleased names.

The unit tests check the `Completed:` prefix, release links, unique ids and
`LAST_REVIEWED`.

Written for the team:

```ts
update: "Window streaming and remote input are implemented on a feature branch; platform integration remains in progress.",
```

Written for you:

```ts
update: "Building. Streaming a window and controlling it remotely both work; next, you'll be able to do it on every desktop platform.",
```
